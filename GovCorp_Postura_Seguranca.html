Sumário Executivo

O GovCorp é uma plataforma SaaS multi-tenant para gestão do ciclo completo de reuniões de Conselhos Deliberativos e Consultivos. Este relatório documenta os controles de segurança implementados e o resultado da auditoria técnica conduzida antes do início dos testes com clientes parceiros.

Todos os itens críticos e médios identificados foram corrigidos. O sistema não possui vulnerabilidades conhecidas em aberto na data deste relatório.

2. Row Level Security (RLS)

Todas as tabelas possuem RLS ativa. Nenhuma policy utiliza a role public. Todos os checks de papel leem do JWT — não da tabela members — eliminando vetores de escalada de privilégios via manipulação de banco.

TabelaGarantia
members Usuário acessa apenas membros do próprio client_id; isolamento enforçado com WITH CHECK
meetings Conselheiro não pode criar/editar/excluir reuniões via chamada direta à API; role verificada no JWT
audit_logs UPDATE e DELETE bloqueados por RLS em nível de banco — logs são tecnicamente imutáveis
server_audit_logs Leitura restrita exclusivamente à role SuperAdmin via JWT

5. Proteção de Dados e Secrets
✓Chaves de API externas
Gemini e Resend armazenadas como Supabase Secrets no servidor. Ausentes no bundle JavaScript entregue ao browser.
✓Arquivos e atas
Acesso via Signed URLs com expiração de 7 dias — sem links públicos permanentes.
✓Injeção de HTML
escapeHtml() e safeUrl() aplicados em todos os campos de entrada do usuário renderizados nos e-mails.
✓CORS
Whitelist de origens explícita em todas as Edge Functions. Nenhum endpoint aceita *.
✓Senhas
Nunca armazenadas em texto plano. Hash gerenciado pelo Supabase Auth (bcrypt).
✓process_audit_log
SECURITY DEFINER com SET search_path = '' e EXECUTE revogado de PUBLIC, anon e authenticated. Executada exclusivamente por triggers internos — não exposta via API REST. Zero warnings no linter do Supabase.
✓Webhook ClickSign
Assinatura HMAC-SHA256 validada em todas as requisições (cabeçalho Content-Hmac) contra secret do servidor. Requisições sem assinatura válida são rejeitadas (401) — fail-closed.
6. Trilha de Auditoria

Todas as ações relevantes — login, criação de reunião, upload de ata, cadastro de membros, convocações — são registradas automaticamente em audit_logs. As políticas RLS garantem que registros existentes não possam ser alterados ou removidos por nenhum usuário, incluindo administradores. A tabela aceita apenas INSERT por usuários autenticados.
